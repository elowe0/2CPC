# P1 — Itérations & tokens
### A5 — `cpc.py answers`
`cpc.py answers <id> --save` (texte collé sur stdin ou `--file`) → `.2cpc/<id>/vN/answers.txt` (vN lu dans l'en-tête `2CPC id vN`). `cpc.py answers <id>` réaffiche la dernière réponse enregistrée. Le skill ajoute une étape : **à chaque réponse collée, l'enregistrer d'abord**.
### A1 — `cpc.py patch`
Applique un fichier de modifications à la dernière version et produit **vN+1**, sans réécrire le plan.
!code text
@replace ## P2 — Stockage        (remplace la section jusqu'au titre de même niveau suivant)
…nouveau contenu…
@after # Décisions actées         (insère après la section)
…
@delete ### A3 — ancienne spec
@meta intro: Nouvelle intro
!end
Cible : le titre exact, ou un préfixe unique. Ambiguïté ou titre introuvable → `ERR`, rien n'est écrit.
### A2 — Décisions reportées
Avec `!decisions` dans vN+1, un tableau Question | Réponse est généré depuis `vN/answers.txt` (A5) : choix, ✓/✗ des approve, rank. Les libellés viennent du plan vN.
### A3 — Changements depuis vN-1
Au build, chaque section est comparée (hash) à celle de vN-1 → badge **modifié** / **nouveau**, plus un bouton « Changements seulement » qui masque les sections identiques. Une ligne `changed: 3 sections` s'ajoute à la sortie CLI.
### A4 — Anciennes réponses
Sous une question reprise dont le libellé ou les options ont changé, on affiche « v(N-1) : <réponse> » en gris. La donnée vient du localStorage de vN-1 (déjà accessible via `prev_key`).
?approve p1 | Specs P1 | A5=`answers --save` + étape dans le skill ; A1=`patch` (@replace/@after/@delete/@meta) ; A2=`!decisions` généré depuis answers.txt ; A3=Badges modifié/nouveau + filtre ; A4=Rappel de l'ancienne réponse
?choice patchsyn | Syntaxe de `patch` | at=Marqueurs `@replace ## Titre`* :: lisible, un fichier ; ids=Ancres explicites `{#id}` sur les titres :: plus robuste, mais il faut les poser ; both=Les deux :: ancre si présente, sinon titre

# P2 — Stockage & todos
!table | Item | Spec
| C1 | Assets copiés une seule fois dans `.2cpc/<id>/assets/<sha8>-<nom>`, référencés en `../assets/…`. Le `rebuild` migre les anciennes versions.
| C3 | `cpc.py gc [<id>] [--keep N]` : supprime les `index.html` des versions plus anciennes que les N dernières (**le `plan.txt` est gardé**, il reste reconstructible), plus les assets orphelins. `--dry-run` par défaut ?
| C4 | En-tête `status: brouillon / actif / fait / archivé` + `cpc.py status <id> fait` (sans nouvelle version). `list` masque `archivé` sauf avec `--all`.
| E1 | `!todo` accepte `KEY=Label`. `cpc.py todo <id> KEY… [--undo]` → `.2cpc/<id>/state.json`. La page affiche ✓ « fait par l'agent » (non décochable) et l'état est reporté en vN+1 par clé.
?approve p2 | Specs P2 | C1=Assets partagés + migration ; C3=`gc` (garde plan.txt) ; C4=Statut + commande ; E1=Todos à clés + `cpc.py todo`
?yesno gcdry | `gc` en simulation par défaut (exige `--yes` pour supprimer) ? | oui

# P3 — Navigation & outillage
!table | Item | Spec
| D1 | `.2cpc/index.html` régénéré à chaque `new` / `patch` / `rebuild` : cartes plan → version, date, statut, todos (state.json), dernière réponse enregistrée. L'avancement en direct vient du localStorage si le navigateur le permet (Chrome partage l'origine `file://`, Firefox non).
| D2 | `~/.2cpc/registry.json` (chemins des projets), mis à jour par `new`. `cpc.py list --all` liste les plans de tous les projets ; chemins morts ignorés.
| D3 | Champ de recherche (Ctrl+F interne, surligne et filtre les sections) + bascule « Sans réponse seulement ».
| D4 | Sommaire collant, avec pastille « n restantes » par section et ● si obligatoire manquante.
| F3 | À chaque `new`, comparer le hash du SKILL.md installé au gabarit → `WARN skill outdated: python install.py`.
| F4 | `cpc.py rebuild --all` : rebuild de tous les projets du registre.
?approve p3 | Specs P3 | D1=Tableau de bord ; D2=Registre + `list --all` ; D3=Recherche + filtre ; D4=Sommaire à pastilles ; F3=Check du skill ; F4=`rebuild --all`
